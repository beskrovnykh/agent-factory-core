# agent-factory

**Autonomous Claude Code sessions driven by tracker tickets.**

Assign a ticket to the agent user in the tracker (Linear), and the runner starts a
headless Claude Code session on the client's server. The session reads the issue,
writes code, opens a PR and hands the ticket back for human sign-off.

- **Roles:** `work` (implement), `verify` (check that the change actually reached
  production, not just that the ticket says so), `intake` (turn a loose request
  into a task), `incident` (on-call).
- **The runner doesn't take the session's word for it.** The handoff is checked
  against a schema; misses go back to the session instead of being patched over.
  Gates (CI, commit ancestry, deployment state) decide `VERIFIED`, not prose.
- **Per-role persistent memory.** Each role keeps its own memory store across
  tasks, with an index rebuilt from the records themselves.
- **One codebase, independent installs.** One install per client, each on its own
  server with its own secrets, queue (Redis) and repo access. Versioned releases.
- Python 3.12, systemd, Redis, ~2,600 tests in CI.

In production since August 2026 for two clients (a trading-analytics platform
and an AI consumer product). This is a public snapshot: client names, hosts and
identifiers are replaced with placeholders (`client-a`, `client-b`, `TASK-N`).
Code comments and docs are in Russian.

Client-agnostic ядро для запуска автономных Claude-сессий по тикетам
(«агент-раннер»). Один исходник — N независимых установок, по одной на
клиента, каждая на своём сервере со своими секретами/redis/доступами.

**Статус: код перенесён как рабочий снимок (05.09.2026), ещё не обобщён.**
`core/` — прямая копия текущей реализации первого клиента (217 тестов зелёные
на новом месте), всё ещё жёстко завязана на Linear (вызовы GraphQL внутри
`runner.py`, не за интерфейсом адаптера) и настраивается через переменные
окружения, а не конфиг-файл клиента. Считать это точкой A, откуда начинается
обобщение, а не готовым ядром.

## Зачем отдельный репозиторий

- Инфраструктурный репозиторий первого клиента деплоит его стек целиком;
  правка общего CI-файла там ревалидирует весь стек, не только раннер.
- `claude-memory` — личная синхронизация конфига/скиллов Claude, не место для
  боевого сервиса с секретами и systemd.
- Раннер должен обслуживать нескольких клиентов независимо — значит ядро не
  должно жить внутри инфраструктуры одного конкретного клиента, и код в этом
  репозитории не должен зависеть от специфики или содержать данные какого-либо
  конкретного клиента.

## Архитектура (дизайн, зафиксирован 05.09.2026)

Один код, N независимых установок — не форк на клиента и не общий
многоарендный процесс. На каждом клиентском сервере: свой redis (просто
очередь, не общий инстанс — иначе нужен сетевой мост между изолированными
периметрами), свои секреты, свой SSH-ключ с доступом только к репозиториям
этого клиента.

Единственная новая абстракция относительно текущей (первый клиент)
реализации — интерфейс адаптера трекера, чтобы ядро не знало про конкретный
Linear/GitHub/что угодно:

```
TrackerAdapter:
  normalize_webhook(raw) -> Event | None
  fetch_task(task_id) -> Task
  set_status(task_id, status: CanonicalStatus)   # IN_PROGRESS|IN_REVIEW|DONE|CANCELED
  assign(task_id, role: CanonicalRole)           # ASSIGNEE|REVIEWER|REPORTER
  post_comment(task_id, text, mode: NEW|APPEND_TO_LAST)
```

Правило маршрутизации «результат — ревьюеру, отказ — постановщику» и сверка
сдачи по схеме (`handoff_misses()` / `repair_handoff()`: раннер не верит
сессии на слово об исходе, промах возвращает ей, а не дописывает) — в ядре,
один раз, не в каждом адаптере.

Полная версия дизайн-документа и история решения — в личной памяти Claude
(вне этого репозитория, не переносить сюда как есть: там вперемешку с
деталями конкретных клиентов).

## Память агентов: постоянная и по ролям (06.09.2026)

**Проблема.** `claude` привязывает память к project scope, а тот — к рабочему
каталогу. Каталог у нас свой на каждую задачу, поэтому память сессии рождалась
пустой и умирала вместе с задачей. На первом клиенте к моменту находки
накопилось 150 осиротевших scope'ов и 23 файла памяти, которые никто больше не
прочитает. Опыт не накапливался в принципе: каждая сессия заново выясняла, как
прогнать тесты локально, как читать прод только на чтение, где какой контур.

**Решение.** Раннер перед запуском сессии подставляет на место памяти симлинк
на постоянный каталог роли:

```
~/.claude/projects/<scope>/memory  →  $AGENT_MEMORY_STORE/agent-<role>
```

* `<scope>` — абсолютный путь рабочего каталога со слэшами через дефис (так
  его считает сам claude);
* `<role>` — `intake` / `incident` / `verify` / `work` (незнакомый `kind` →
  `work`, как и везде в раннере).

**Ключ — роль, а не задача и не слот.** У ролей разный опыт: приёмщику незачем
знать, как дежурный гасит инцидент. Дробить ещё и по слотам смысла нет — это
раскололо бы один опыт надвое без причины.

**Индекс собирается программой из полей записей** (DEV-85, 14.09.2026). На
старте роли `MEMORY.md` пишется заново по тому, что фактически лежит в
каталоге: имя и описание берутся из frontmatter, порядок задаёт `kind`
(ограничения первыми), формат один.

До этого пересборка только ДОБАВЛЯЛА строки, а дубль искала подстрокой
`(файл.md)` — при том, что писателей формата было два, и во втором скобки
содержат абсолютный путь. Совпадения не находилось никогда: в живом сторе
client-a три записи стояли дважды, индекс дорос до 26 591 байта при потолке
12 000, и роль перестала видеть методологию.

Что сборку переживает: текст человека выше маркера; описание, написанное в
индексе, если в самом файле описания нет; строка, дописанная параллельной
сессией, — она уходит в шапку, а не теряется. Что не переживает: дубли,
порядок строк и записи с `drop: true`. Прежний индекс при первой сборке
уводится в `_before-index-rebuild/`, а не заменяется.

Описание в строке индекса режется по `INDEX_DESC_MAX` (80 знаков). Сам файл не
трогается: строка каталога отвечает на один вопрос — открывать ли файл.

Потолок здесь не косметика, а **единственный рычаг на размер проектного
индекса**. `AGENT_MEMORY_INDEX_MAX` его не ограничивает: индекс грузит сам
claude из каталога памяти, на который раннер поставил симлинк, а переменная
участвует только в арифметике «сколько осталось методологии». Уменьшить её
значит уменьшить долю методологии в контексте, а не контекст.

Замер на живом сторе client-b — сколько худшая роль (`verify`, 59 записей)
получает в контекст всего, против наблюдавшегося потолка чтения 24 400 Б:

| потолок строки | в контекст | от потолка чтения |
|---|---|---|
| 100 | 21 490 Б | 88% |
| 90 | 20 508 Б | 84% |
| **80** | **19 769 Б** | **81%** |
| 70 | 18 724 Б | 77% |

Сегодня роль получает 18 457 Б (76%) при индексе, который врёт: строки
разошлись с файлами у 82 записей из 101. Потолок 80 покупает верный индекс за
четыре процентных пункта запаса. Запаса он при этом не создаёт: при 59 записях
индекс упирается в их число, а не в длину строк — это работа для свёртки.

**Настройка.** `AGENT_MEMORY_STORE` — корень стора в конфиге инстанса. Пусто →
механизм выключен, поведение прежнее. Путь к стору клиент-специфичен, ядро его
не знает. `AGENT_METHODOLOGY_TRACKS` — дисциплины инсталляции через запятую
(`разработка`, `маркетинг`); пусто → методология показывается вся.

- `docs/memory-store-setup.md` — как завести новый стор (проверено заведением и снятием четвёртого).
- `docs/memory-maintenance.md` — **память портится сама, и отказ бесшумный.** Чем мерить, какие пороги, что делать по симптому, и чего делать нельзя.

**Границы, которые механизм соблюдает:**

* реальный (не symlink) каталог на месте памяти **не подменяется** — там могут
  быть чужие записи, спрятать их молча нельзя;
* любой сбой (стор недоступен, нет прав) — предупреждение в лог, сессия
  стартует с одноразовой памятью. Память не обязательное условие работы.

**Что осталось на потом:** засев ролей (перенести в каждую релевантное из
общего стора — разовая работа руками), свёртка отдельным прогоном (рабочей
сессии её поручать нельзя: указание «сожми индекс», адресованное той же
сессии, которая сдаёт задачу, не выполнила ни одна за четверо суток),
автоматизация обратного слива полезного из блокнотов ролей в общий стор.

## Что не решено

- **Главное:** `runner.py` внутри всё ещё жёстко зовёт Linear GraphQL
  напрямую (функция `linear_graphql` и вызовы по всему файлу), а не через
  `TrackerAdapter`. Сейчас это Linear-раннер, который просто физически лежит
  в отдельном репозитории — не client-agnostic ядро. Вынесение вызовов за
  интерфейс — следующий шаг, отдельно от переноса.
- `prompt.py` (900+ строк) — сам текст контракта, тоже написан в терминах
  Linear/MR. Насколько он должен стать шаблоном с плейсхолдерами против
  «одна реализация на клиента, поверх общего ядра» — не решено.
- Формат конфига клиента (репозитории, роли, включённые шаги контракта) —
  черновик в разделе «Архитектура» выше, не проверен.
- Как код ядра долетает до сервера клиента без доступа этого сервера к
  инфраструктурному репозиторию первого клиента — открытый вопрос.
